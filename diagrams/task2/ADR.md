### Функциональные требования (ключевые для выбора архитектуры)

| № | Use Case | Ключевое требование к архитектуре |
|---|----------|-----------------------------------|
| 1 | Обнаружение драк и задавливания | Видеоаналитика должна работать офлайн с задержкой <5 сек |
| 2 | Управление кормушками/поилками | Поддержка разных производителей (Modbus, OPC-UA) |
| 3 | Контроль запасов кормов | Прогнозирование расхода, интеграция с ERP |
| 4 | Предоставление метрик в BI | REST API / Prometheus |
| 5 | Мобильное приложение | Offline-first, push-уведомления |

### Нефункциональные требования (ключевые для выбора архитектуры)

| № | Требование | Влияние на архитектуру |
|---|------------|------------------------|
| NFR-2 | Оповещение < 5 секунд | Видеоаналитика должна быть на edge, не в облаке |
| NFR-4 | Полная работа без интернета | Edge-агент должен быть самодостаточным |
| NFR-5 | Расширяемость | Микросервисы легче расширять, чем монолит |
| NFR-6 | Масштабируемость (неограниченное количество ферм) | Горизонтальное масштабирование центра |
| NFR-8 | Совместимость с разным оборудованием | Слой IoT Gateway с адаптерами |

### Решение

#### Диаграмма контейнеров (C2) - Выбранное решение (Микросервисная архитектура)

#### Описание компонентов выбранного решения

**Edge-уровень (на каждой ферме):**
- `Video Analyzer` (Python + YOLOv8 + GPU) — детекция драк, задавливания, подсчёт поголовья. Работает офлайн.
- `IoT Gateway` (Node-RED + Mosquitto) — сбор телеметрии, управление кормушками/поилками, адаптеры под Modbus/OPC-UA.
- `Edge Sync Agent` (Go) — асинхронная синхронизация с центром, retry-механизмы, batch-отправка.
- `Local Cache` (SQLite / TimescaleDB) — буферизация данных до 30 дней при обрыве связи.
- `Local API` (FastAPI) — локальный веб-интерфейс для оператора, WebSocket для алертов.

**Центральные сервисы:**
- `API Gateway` (Kong) — маршрутизация, авторизация, rate limiting.
- `Auth Service` (Keycloak) — аутентификация, управление ролями (оператор, ветврач, админ).
- `Device Manager` (Kotlin + Spring) — управление устройствами, конфигурации.
- `Alert Engine` (Go + Temporal) — глобальные правила оповещений, эскалация.
- `Inventory Service` (Kotlin) — управление запасами кормов, прогнозирование.
- `Analytics Service` (Python + Spark) — аналитика здоровья животных, тренды.
- `Notification Service` (Go) — push (FCM/APNS), email, SMS.
- `Central DB` (PostgreSQL + TimescaleDB) — данные всех ферм.
- `Redis Cluster` — кэш, сессии, очереди.

**Интеграция с существующей платформой:**
- Kafka — шина данных (уже существует)
- ClickHouse — DWH для аналитики
- Power BI — отчёты

#### Логика принятия решений и выбора технологий

| Компонент | Выбор | Альтернатива | Обоснование |
|-----------|-------|--------------|-------------|
| **Архитектура центра** | Микросервисы | Монолит | Позволяет независимо масштабировать аналитику, алерты, управление устройствами |
| **Видеоаналитика** | YOLOv8 + DeepSORT | Detectron2 | Лучшее соотношение скорость/точность, работает на GPU |
| **IoT Gateway** | Node-RED | Telegraf | Визуальное программирование, быстрая разработка адаптеров |
| **MQTT Broker** | Mosquitto | EMQX | Лёгкий, надёжный, малый footprint |
| **Edge Sync** | Go | Python | Высокая производительность, горутины, малый footprint |
| **Local Cache** | SQLite / TimescaleDB | Redis | Встраиваемость, ACID, работа с временными рядами |
| **API Gateway** | Kong | Nginx | Плагины авторизации, rate limiting, Lua-расширяемость |
| **Auth** | Keycloak | Auth0 | Open Source, OAuth2/OIDC, интеграция с AD |
| **Device Manager** | Kotlin + Spring Boot | Go | Надёжность, типобезопасность, экосистема Spring |
| **Alert Engine** | Go + Temporal | Python + Celery | Durable execution, таймеры, эскалация |
| **Analytics** | Python + Spark | Pandas | Масштабируемость при росте данных |
| **Central DB** | PostgreSQL + TimescaleDB | CockroachDB | TimescaleDB для временных рядов (телеметрия) |
| **Cache** | Redis Cluster | Memcached | Поддержка структур данных, pub/sub |
| **Мобильное приложение** | React Native | Flutter | Кроссплатформенность, экосистема |
| **Веб-панель** | React + Grafana | Vue.js | Grafana для готовых дашбордов |

#### Компромиссы, принятые в решении

| Компромисс | Выбранное решение | Обоснование |
|------------|-------------------|-------------|
| **Микросервисы vs Монолит (в центре)** | Микросервисы | Сложнее в разработке, но легче масштабировать и независимо обновлять |
| **gRPC vs REST** | gRPC для внутренних вызовов, REST для API Gateway | gRPC быстрее, REST стандарт для внешних систем |
| **Batch-синхронизация vs Real-time** | Batch 5-10 минут | Соответствует требованиям (допустимая задержка), экономит трафик |
| **Eventual vs Strong consistency** | Eventual для edge↔центр, strong для центральных сервисов | Edge может работать офлайн |
| **Temporal vs простой таймер** | Temporal | Сложнее в эксплуатации, но даёт durable execution для алертов |
| **SQLite vs PostgreSQL на edge** | SQLite для маленьких ферм, TimescaleDB для больших | SQLite легче, TimescaleDB нужен для большого объёма телеметрии |
| **Kafka vs RabbitMQ** | Используем существующий Kafka | RabbitMQ проще, но Kafka уже развёрнут в компании |

### Альтернативы

#### Диаграмма контейнеров (C2) - Альтернативное решение (Монолит ядра)

> 📄 **Файл диаграммы:** [`../task2/container-diagram-alternative.puml`](../task2/container-diagram-alternative.puml)

#### Описание альтернативного решения

**Edge-уровень** (аналогичен основному решению):
- Видеоаналитика, IoT Gateway, Edge API, Local Storage

**Центр (монолит):**
- `Core Monolith` (Spring Boot / .NET) — один сервис, содержащий всё: управление фермами, аналитику, отчёты, пользователей
- `API Gateway` (Kong) — маршрутизация, авторизация
- `Notification Service` (Go) — push-уведомления
- `Central DB` (PostgreSQL) — все данные
- `Redis` — кэш, сессии

#### Сравнение альтернатив и логика выбора

| Критерий | Основное решение (Микросервисы) | Альтернативное решение (Монолит) |
|----------|--------------------------------|----------------------------------|
| **Сложность разработки** | Высокая | Низкая |
| **Скорость старта** | Медленнее | Быстрее |
| **Масштабируемость** | Высокая (по сервисам) | Низкая (только вертикально) |
| **Независимые деплои** | ✅ Да | ❌ Нет |
| **Отказоустойчивость** | Выше (изоляция сервисов) | Ниже (один сервис падает — всё падает) |
| **Расширяемость (NFR-5)** | ✅ Легко добавить новый сервис | ❌ Тяжело (менять монолит) |
| **Масштабируемость ферм (NFR-6)** | ✅ Горизонтально | ❌ Только вертикально |
| **Сложность эксплуатации** | Высокая | Низкая |

**Почему выбрано микросервисное решение:**
1. Требование NFR-6 (неограниченное количество ферм) требует горизонтального масштабирования
2. Требование NFR-5 (расширяемость) легче обеспечивается микросервисами
3. Разные сервисы имеют разные требования к ресурсам (Analytics требует много CPU, Notification — много сети)
4. Монолит быстро станет узким местом при росте числа ферм

**Почему альтернатива не выбрана:**
- Монолит подходит для MVP с 5-10 фермами, но не для масштабирования
- Обновление любого функционала требует передеплоя всего ядра
- При отказе монолита вся центральная платформа недоступна

### Недостатки, ограничения, риски выбранного решения

#### Недостатки

1. **Высокая сложность разработки** — требуется больше времени на настройку межсервисного взаимодействия
2. **Сложность отладки** — трассировка запросов через несколько сервисов
3. **Дополнительные сетевые вызовы** — латентность между сервисами
4. **Управление транзакциями** — распределённые транзакции сложнее (Saga pattern)

#### Ограничения

1. **Temporal требует отдельной инфраструктуры** — дополнительный компонент для Alert Engine
2. **Keycloak сложен в эксплуатации** — требует специальных знаний
3. **Spark требует ресурсов** — для Analytics нужны отдельные узлы

#### Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Сетевые задержки между микросервисами | Средняя | Среднее | gRPC, локальный кэш, асинхронные вызовы |
| Сложность мониторинга | Средняя | Среднее | Prometheus + Grafana, distributed tracing (Jaeger) |
| Управление конфигурациями | Средняя | Среднее | Spring Cloud Config, K8s ConfigMaps |
| Рост числа ферм → нагрузка на центральные сервисы | Высокая | Высокое | Горизонтальное масштабирование каждого сервиса независимо |
| Отказ Kafka | Низкая | Высокое | Кластер Kafka, репликация |

#### Компромиссы, зафиксированные в решении

| Компромисс | Решение | Обоснование |
|------------|---------|-------------|
| **Сложность разработки vs Масштабируемость** | Выбрали масштабируемость | MVP делается под масштабирование на десятки ферм |
| **Монолит vs Микросервисы** | Микросервисы | Хотя сложнее, соответствует NFR-5 и NFR-6 |
| **Синхронные vs Асинхронные вызовы** | Асинхронные через Kafka для событий | Синхронные через gRPC для команд, асинхронные для событий |
| **Temporal vs Simple Scheduler** | Temporal | Нужен для надёжной эскалации алертов (health-воркеры) |
